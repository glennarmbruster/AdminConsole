TWO PARTS. The first is a plain-language write-up for the people who have to
approve this. The second, below the double line, is the build instruction for
the engineer implementing it.


--------------------------------------------------------------------------------
1. WHAT IS BEING ASKED FOR, IN ONE PARAGRAPH
--------------------------------------------------------------------------------

The Admin Console is an internal PowerShell toolkit used by messaging
administrators to answer day-to-day mail questions -- where a message went, who
has access to a mailbox, why a delivery failed. Several of those questions can
only be answered by systems outside Microsoft 365: Proofpoint, which filters
inbound mail and quarantines what it judges malicious; Proofpoint Secure Email
Relay, which carries our application mail; and SendGrid, which also sends
application mail. Each offers an API. Using them requires credentials. This
document sets out what those credentials can do, how they will be protected,
and asks for a decision on one point that is not mine to make.


--------------------------------------------------------------------------------
2. THREE CREDENTIALS, THREE DIFFERENT SHAPES
--------------------------------------------------------------------------------

This is the part most easily got wrong, so it is set out in full. These are not
three copies of the same thing and the design does not treat them as such.

  2.1  PROOFPOINT PRIMARY POD -- the mail gateway

    WHAT IT IS FOR
      Searching what the gateway did with a message, and RELEASING A MESSAGE
      FROM QUARANTINE. Release is the reason this credential exists: the daily
      ticket is "a legitimate message was quarantined and the recipient needs
      it", and today that is done by hand in a separate console.

    PERMISSIONS
      Read, plus ONE WRITE: release a named message from quarantine.
      It cannot send mail. It cannot alter filtering policy.

    HOW IT AUTHENTICATES
      A Proofpoint administrator account holding a role that includes REST API
      access. Two points that affect the request rather than the design:

        * The API is served on PORT 10000, not the standard web port. Network
          access from the administrator workstation must be confirmed.

        * PROOFPOINT ON DEMAND ADMINISTRATORS MUST RAISE A SUPPORT TICKET WITH
          PROOFPOINT to have the REST API role enabled. It is not self-service
          and it has a lead time. This should be started early.

      THE EXACT AUTHENTICATION MECHANISM IS RECORDED AS UNCONFIRMED. The
      publicly available documentation does not state it unambiguously, and I
      am not prepared to design against a guess. It will be confirmed with
      Proofpoint support at the same time the API role is requested. The
      credential-handling design below is deliberately shape-agnostic and
      accommodates either a single token or a username-and-secret pair.

  2.2  PROOFPOINT SECURE EMAIL RELAY (SER POD) -- application mail

    WHAT IT IS FOR
      Reporting and message events only. Looking up what happened to
      application mail that went out through the relay.

    PERMISSIONS
      READ ONLY. No send. No configuration change.

      THIS IS WORTH STATING CLEARLY BECAUSE SER IS A SENDING PLATFORM. We are
      asking for reporting access to a system that can send mail, and we are
      not asking for the ability to send. If the scope offered cannot separate
      the two, that is a material change and comes back for review rather than
      being accepted quietly.

    HOW IT AUTHENTICATES
      OAuth 2.0 client credentials: a CLIENT ID and a CLIENT SECRET are
      exchanged for a short-lived bearer token, and the token is used on
      subsequent calls. Two long-lived values to protect, plus a short-lived
      token that is itself sensitive and is handled under the same rules.

  2.3  SENDGRID -- application mail

    WHAT IT IS FOR
      Finding out why our mail is not reaching a customer, and REMOVING THE
      ADDRESS FROM THE SUPPRESSION LIST that is stopping it -- bounces, blocks,
      spam reports and invalid addresses.

    PERMISSIONS
      SendGrid keys are Restricted Access with each scope independently set to
      No Access, Read Access or Full Access. We need:

          Suppressions ................ Full Access
          Mail Send ................... No Access
          every other scope ........... No Access

      READ ACCESS IS NOT SUFFICIENT AND IT IS WORTH BEING PRECISE ABOUT WHY.
      Read Access permits GET only. Removing an address from a suppression list
      is an HTTP DELETE. A read-only key could tell us the address is
      suppressed and could not do the one thing the administrator opened the
      tool to do.

      MAIL SEND STAYS AT NO ACCESS. Because SendGrid's scopes are independent,
      this key can remove a suppression and CANNOT SEND A SINGLE EMAIL, cannot
      alter sender authentication, cannot change account settings and cannot
      touch billing.

    Note also that SendGrid does not permit a key to hold billing permissions
    alongside any other permission, and a key cannot exceed the permissions of
    the person who creates it. Both work in our favour.

  2.4  SUMMARY TABLE

    Credential          Values held              Reads   Writes
    ----------------    ---------------------    -----   ------------------------
    Proofpoint POD      TBC -- see 2.1           yes     release from quarantine
    Proofpoint SER      client id + secret       yes     none
    SendGrid            one API key              yes     remove a suppression

    NO CREDENTIAL IN THIS SET CAN SEND MAIL. There are exactly two write
    operations across all three platforms and both are bounded, per-item,
    confirmed by the operator and audited. Section 7 covers them.


--------------------------------------------------------------------------------
3. THE REQUIREMENT WE ARE DESIGNING AGAINST
--------------------------------------------------------------------------------

Stated plainly, and treated as non-negotiable:

    The credentials must not be recoverable by anyone who obtains a copy of the
    toolkit, its configuration files, its logs, or its reports. They must not
    sit in a script, in a JSON file, or in any file that can be read.

Everything below follows from that sentence.


--------------------------------------------------------------------------------
4. THE OPTIONS THAT WERE CONSIDERED AND REJECTED
--------------------------------------------------------------------------------

Documented because "why not just..." is the first question in every review of
this kind, and answering it once here is cheaper than answering it four times
in a meeting.

  REJECTED -- PLAINTEXT IN A CONFIGURATION FILE.

    The toolkit already reads a Tenant.json and a Tools.json. Adding the keys
    there would take five minutes and would fail the requirement outright. Any
    person, process or backup job that can read the toolkit folder would hold
    live credentials. Not proposed.

  REJECTED -- WINDOWS DPAPI ENCRYPTION (Export-Clixml / ConvertTo-SecureString).

    This is the answer most PowerShell documentation gives, and it is genuinely
    encrypted -- but it is encrypted TO A USER ACCOUNT ON A MACHINE. Anything
    running as that user on that machine decrypts it silently, including
    malware running in that user's session and including anyone who can obtain
    that user's profile.

    It also gives us NO CENTRAL AUDIT -- nobody can answer "who used this
    credential and when" -- and NO ROTATION PATH. When a key is rotated, or
    when the person holding it changes role, there is no inventory telling
    anyone that a copy exists on a particular workstation.

    For a personal script this is reasonable. For credentials that can release
    mail from a security quarantine it is not, and I would rather say so up
    front than have it found in review.

  REJECTED -- A SHARED SERVICE ACCOUNT HOLDING THE CREDENTIALS.

    Moves the problem rather than solving it, and removes individual
    attribution from every quarantine release -- which is the one thing the
    audit trail on this integration most needs to establish.


--------------------------------------------------------------------------------
5. THE TWO OPTIONS THAT MEET THE REQUIREMENT
--------------------------------------------------------------------------------

OPTION A -- RETRIEVE FROM CYBERARK AT RUN TIME (the strategic answer)

  CyberArk is already our sanctioned credential store and is built for exactly
  this. The mechanism is the Central Credential Provider (CCP): the toolkit
  makes an authenticated request to the CCP endpoint naming an Application ID,
  a Safe, and an account object, and receives the secret back in memory for the
  duration of the call.

  THE IMPORTANT PROPERTY, AND THE ONE THAT USUALLY NEEDS EXPLAINING: there is
  no chicken-and-egg problem. The toolkit does not hold a password in order to
  fetch a password. CyberArk authenticates the CALLER BY IDENTITY -- the
  registered Application ID, restricted to a specific machine, a specific
  operating-system user, a specific path, and in our environment a client
  certificate. Nothing sensitive is stored on the workstation at any point.

  WHAT WE GET:
    * No credential on disk, at all, ever.
    * Central rotation. The value changes in CyberArk; the toolkit picks up the
      new one on its next call with no redeployment and no user action. With
      three credentials on three rotation schedules this matters more than it
      would with one.
    * A real audit trail. CyberArk records every retrieval, by whom, from
      where, and when.
    * Immediate revocation. Disabling the Application ID cuts access at once.

  WHAT IT COSTS, STATED HONESTLY:
    * An onboarding request to the CyberArk team: an Application ID, a Safe,
      and the account objects.
    * A design conversation about restriction. CyberArk's usual controls pin an
      Application ID to an executable path and hash. Our "executable" is
      powershell.exe, which is a weak restriction on its own, so the real
      controls become the OS user, the machine, and the client certificate. The
      CyberArk team will have a view on this and it is the part of the request
      most likely to need discussion.
    * Application IDs are normally granted to applications with a support
      model, not to an individual's tooling. Whether this toolkit qualifies is
      a policy judgement, and it is the one decision in this document that is
      not mine to make.

OPTION B -- ENTER THE CREDENTIAL PER SESSION, HELD ONLY IN MEMORY (the
            immediate answer)

  The administrator retrieves the credential from the CyberArk web interface in
  the normal way and pastes it into the toolkit when it is first needed. It is
  held in memory for that console session only and is gone when the console
  closes.

  WHAT WE GET:
    * Nothing is ever written to disk. The requirement in section 3 is met.
    * CyberArk remains the system of record and its existing checkout audit
      still applies -- we simply do the checkout by hand.
    * No new integration, no Application ID, no onboarding queue. This can
      start the day the credentials are issued.

  WHAT IT COSTS:
    * Each credential is pasted by a human, which means it is briefly visible
      and briefly on the clipboard.
    * A prompt on first use per credential per session. In practice this is a
      small number of prompts a day, because the prompt is triggered only by a
      tool that actually needs that specific credential and each session
      remembers it thereafter. An administrator who only releases a quarantined
      message is never asked for the SendGrid or SER credentials.
    * No automation. Anything unattended is out of scope, which is correct for
      this toolkit -- it is interactive and has no scheduled runs.


--------------------------------------------------------------------------------
6. RECOMMENDATION
--------------------------------------------------------------------------------

DO BOTH, IN THIS ORDER.

  NOW      Build Option B. It meets the stated requirement, needs no approval
           beyond the credentials themselves, and gets the capability into use
           so its value can be judged on evidence rather than on a proposal.

  THEN     Request CyberArk onboarding for Option A once the tools have a
           demonstrated usage record.

The sequencing is the main recommendation of this document. An onboarding
request that says "this toolkit handled N quarantine releases and N suppression
removals last month and we would like to remove the manual checkout step" is a
materially easier request to evaluate than one describing something
hypothetical. It also means that if the answer is no, we still have a working
capability rather than nothing.

The switch between the two is a small change. The toolkit retrieves every
credential through a single function, so moving from a prompt to a CyberArk call
changes one function and nothing else. This is specified in Part 2 and is the
reason the interim option does not become throwaway work.


--------------------------------------------------------------------------------
7. CONTROLS
--------------------------------------------------------------------------------

Commitments, not aspirations. Each is enforced in code and checked by the
toolkit's automated self-test before release.

  1. NO CREDENTIAL IS EVER WRITTEN TO DISK by the toolkit. Not to
     configuration, not to the audit log, not to a report, not to a temporary
     file. This includes the short-lived SER bearer token.

  2. NO CREDENTIAL APPEARS IN ANY OUTPUT. Not on screen, not in an error
     message, not in a progress line.

     THE SPECIFIC HAZARD IS ERROR HANDLING. API failures can surface request
     detail, and a handler that dumps an exception verbatim can print an
     Authorization header. All API error text is scrubbed before display.

  3. THE AUDIT LOG RECORDS THE ACTION, NEVER THE CREDENTIAL. What
     authenticated a call is not part of any question the audit log exists to
     answer, and recording it would turn the log into a credential store.

  4. LEAST PRIVILEGE AT ISSUE.

       Proofpoint POD    read, plus release-from-quarantine. No send.
       Proofpoint SER    read only. Explicitly no send.
       SendGrid          Suppressions Full Access. Mail Send NO ACCESS.
                         Every other scope No Access.

     No credential in this set can send mail.

  5. THE CREDENTIAL DIES WITH THE SESSION. Closing the console clears all of
     them. A "Forget credentials" action clears them sooner without restarting.

  6. ROTATION SCHEDULES ARE AGREED BEFORE THE CREDENTIALS ARE ISSUED, not
     after. A key with no rotation date is a permanent key.

  7. THERE ARE EXACTLY TWO WRITE OPERATIONS AND BOTH ARE BOUNDED.

     7a. RELEASING A MESSAGE FROM PROOFPOINT QUARANTINE.

         This is the highest-consequence action in the entire integration and
         it is treated as such. A quarantined message was quarantined because a
         security control judged it malicious. Releasing it delivers it to a
         user. That is a legitimate administrative action -- false positives
         are real and people need their mail -- but it is a security control
         being deliberately overridden, and it must be attributable to a named
         person every single time.

         Rules, all enforced in code:
           * ONE MESSAGE PER ACTION. No bulk release, no "release all", no
             release by search result set. If ten messages need releasing, that
             is ten confirmed actions by a person.
           * THE OPERATOR SEES WHY IT WAS QUARANTINED BEFORE CONFIRMING.
             Classification, sender, subject and recipient are displayed on the
             confirmation, so the decision is informed rather than reflexive.
           * EVERY RELEASE IS AUDITED with the message identifier, the
             recipient, the operator, the timestamp and the result -- success
             or failure. A failed release is logged as a failure, never
             silently.

     7b. REMOVING AN ADDRESS FROM A SENDGRID SUPPRESSION LIST.

         Rules:
           * ONE NAMED ADDRESS PER ACTION.
           * THE BULK ENDPOINTS ARE PROHIBITED IN CODE. SendGrid offers calls
             that delete an entire suppression list in one request. Those are
             never called by any tool in this toolkit under any circumstances,
             and the automated self-test fails the build if the pattern
             appears. An accidental bulk deletion would silently restore
             delivery to every address the platform had ever suppressed --
             including genuine spam complaints -- and there is no undo.
           * THE OPERATOR SEES WHICH LIST the address is on before removing it.
             A hard bounce and a spam complaint are different decisions.
           * EVERY REMOVAL IS AUDITED with the address, operator, timestamp and
             result.

     Everything else the toolkit does on all three platforms is read.


--------------------------------------------------------------------------------
8. RESIDUAL RISK, STATED WITHOUT SOFTENING
--------------------------------------------------------------------------------

A security review will find these anyway. Better that they come from us.

  * ANYTHING HELD IN MEMORY CAN IN PRINCIPLE BE RECOVERED FROM MEMORY. The
    toolkit uses .NET SecureString, which keeps values encrypted in memory and
    out of PowerShell transcripts and command history. It is a meaningful
    control against casual exposure. It is NOT protection against an attacker
    who already has code execution and debug rights on the workstation. Anyone
    presenting SecureString as a vault is overselling it, and this document
    does not.

    The controls that actually matter for that threat are the ones already
    applied to administrator workstations -- endpoint protection, privileged
    access management, and the fact that an attacker at that level of access
    has better targets available.

  * UNDER OPTION B EACH CREDENTIAL PASSES THROUGH THE CLIPBOARD AND IS BRIEFLY
    VISIBLE ON SCREEN during paste. Inherent to manual entry, and one of the
    reasons Option A is the strategic target.

  * THE QUARANTINE RELEASE PERMISSION IS THE MOST CONSEQUENTIAL THING IN THIS
    REQUEST. A leaked POD credential could be used to release quarantined
    messages -- that is, to deliver mail that our own security control had
    already judged malicious. The controls in 7a make every release
    attributable and prevent bulk action, which limits both the scale and the
    deniability of misuse; they do not make the permission harmless. If the
    review's conclusion is that release should stay in the Proofpoint console
    and out of this toolkit, that is a defensible position and the toolkit
    still has value as a read-only search tool.

  * THE SENDGRID KEY CAN UN-SUPPRESS ADDRESSES. A leaked key could remove
    addresses from bounce, block and spam-report lists. The consequences are
    deliverability and sender-reputation ones -- mail resuming to people who
    complained or hard-bounced -- rather than confidentiality ones, and
    SendGrid's own activity data makes the change visible after the fact. It is
    a far smaller exposure than a Mail Send permission, which is precisely why
    Mail Send is not being requested, but it is not nothing.

  * READ ACCESS STILL READS. All three platforms hold sender and recipient
    addresses and message subjects. Exposure of any of these credentials would
    be a confidentiality event even where no write is possible. The scoping in
    control 4 limits the blast radius; it does not eliminate it.

  * SUPPRESSION REMOVAL AND QUARANTINE RELEASE ARE JUDGEMENT CALLS, NOT
    MECHANICAL ONES. The tools surface the reason -- which list, which threat
    classification -- before either action, so the operator decides knowingly.
    The audit log records who decided.

  * OPTION A INTRODUCES A DEPENDENCY ON CCP AVAILABILITY. If the CCP endpoint
    is unreachable the affected tools stop working. They fail with a clear
    message rather than falling back to any stored value -- there is no stored
    value to fall back to, by design.

10. SUMMARY FOR SOMEONE READING ONLY THIS SECTION
--------------------------------------------------------------------------------

Three API credentials are needed for an internal messaging support tool: the
Proofpoint mail gateway, Proofpoint Secure Email Relay, and SendGrid.

NONE OF THEM CAN SEND MAIL. Two write operations exist in total. The first
releases a single named message from Proofpoint quarantine -- the everyday
"my legitimate email was blocked" ticket. The second removes a single email
address from a SendGrid suppression list -- the everyday "our mail is not
reaching this customer" ticket. Both are confirmed by the operator one item at a
time, both are recorded in the toolkit's audit log against a named person, and
the bulk-action calls that both platforms offer are prohibited in code.

No credential will ever be written to disk in any form. CyberArk remains the
system of record. In the short term the administrator checks each credential out
of CyberArk by hand and the tool holds it in memory for that session only. In
the longer term, subject to approval, the tool retrieves them from CyberArk
directly, which removes the manual step and gives a central audit of every
retrieval. The code is written so that moving from the first to the second
changes one function.

The one item needing a decision rather than a resource is whether quarantine
release belongs in this toolkit at all. Section 8 sets out the case both ways.

PART 2 -- BUILD INSTRUCTION FOR DEVIN
--------------------------------------------------------------------------------

Paste everything from here down. Part 1 above is background and does not need to
be read to do the work, though section 7 is the list of things that must be true
when you are finished.

--------------------------------------------------------------------------------
WHAT TO BUILD, AND WHY NOW
--------------------------------------------------------------------------------

Build the credential-retrieval layer NOW, before any credential exists.

There are no keys yet. That is deliberate and it is the point: when the keys
arrive I want to paste them into a working tool, not start building. Every tool
that later talks to Proofpoint or SendGrid must be written against this
interface from its first line, so that nothing is ever retrofitted.

You are building ONE FUNCTION in Common.ps1 plus its supporting pieces. YOU ARE
NOT BUILDING A PROOFPOINT OR SENDGRID TOOL IN THIS TASK. The tools come later
and will be specified separately.

--------------------------------------------------------------------------------
THE CONTRACT
--------------------------------------------------------------------------------

Add to Common.ps1:

    Get-ApiSecret -Service <string> [-Purpose <string>] [-Force]

        Returns a PSCustomObject:

            Ok        [bool]           false if the operator cancelled
            Service   [string]         echo of -Service
            User      [string]         principal / client id half, or ''
            Secret    [SecureString]   the secret half
            Source    [string]         'Prompt' or 'CCP'
            Reason    [string]         why Ok is false, when it is false

    Clear-ApiSecret [-Service <string>]

        Clears one service, or all when -Service is omitted. Calls .Dispose()
        on each SecureString, then removes the entry. MUST ALSO CLEAR ANY
        CACHED OAUTH TOKEN for that service -- see the SER section.

    Get-ApiSecretState

        One row per known service: Service, Loaded (bool), AcquiredAt. NEVER
        returns a secret. This lets the console show what is loaded without any
        tool touching the values.

--------------------------------------------------------------------------------
THREE SERVICES, THREE SHAPES. DRIVE IT FROM A TABLE.
--------------------------------------------------------------------------------

Do not build a single-value interface and bolt the others on later.

    $script:ApiSecretDefs = [ordered]@{

        'ProofpointPod' = @{
            Label       = 'Proofpoint (mail gateway)'
            NeedsUser   = $true
            UserLabel   = 'API user'
            SecretLabel = 'Password'
            Help        = 'Requires the REST API role. API is on port 10000.'
        }

        'ProofpointSer' = @{
            Label       = 'Proofpoint Secure Email Relay'
            NeedsUser   = $true
            UserLabel   = 'Client ID'
            SecretLabel = 'Client Secret'
            Help        = 'OAuth2 client credentials. Reporting scope only.'
            OAuth       = $true
        }

        'SendGrid' = @{
            Label       = 'SendGrid'
            NeedsUser   = $false
            UserLabel   = ''
            SecretLabel = 'API Key'
            Help        = 'Restricted Access: Suppressions = Full Access, everything else No Access.'
        }
    }

Adding a service is adding a row. Same reason the Unified Lookup hand-off is a
table: the extension mechanism should be visible rather than buried in
branching.

THE PROOFPOINT POD SHAPE IS PROVISIONAL. Its exact authentication mechanism is
NOT YET CONFIRMED -- the vendor documentation I can reach does not state it
unambiguously and a support ticket is open. The table entry above assumes a
user-and-password pair because that accommodates the widest range of outcomes,
but treat it as a placeholder. Record this in UNVERIFIED.md. DO NOT WRITE ANY
CODE THAT CALLS THE POD API in this task -- only the credential plumbing. When
the mechanism is confirmed, changing it should mean changing this one table row.

--------------------------------------------------------------------------------
THE SER OAUTH TOKEN -- A SECOND SECRET WITH A CLOCK ON IT
--------------------------------------------------------------------------------

SER does not accept the client secret directly. The client id and secret are
exchanged for a SHORT-LIVED BEARER TOKEN which is then used on API calls.

That token is itself a credential and obeys every rule in this document: never
on disk, never in output, never in the audit log.

Build:

    Get-SerAccessToken [-Force]

        Returns a SecureString bearer token. Caches it in $global: alongside
        the credentials WITH ITS EXPIRY. Returns the cached token while it is
        still valid; exchanges for a new one when it is not.

THREE THINGS TO GET RIGHT:

  * A TOKEN REFRESH MUST NOT PROMPT THE OPERATOR. It uses the cached client
    credentials. If the operator is asked to paste a client secret again
    forty minutes into a session because a token expired, the design has
    failed.

  * TREAT THE TOKEN AS EXPIRED EARLY. Subtract a safety margin -- 60 seconds is
    ample -- from the stated lifetime. A token that expires between the check
    and the call produces a 401 that looks like a credential problem and sends
    somebody debugging in the wrong direction.

  * A 400 FROM THE TOKEN ENDPOINT MEANS THE CREDENTIALS ARE WRONG OR EXPIRED,
    not that the API is down. An 'invalid_client' response means the pair was
    rejected and a replacement key must be created. Say that in the error text
    -- it is the single most useful thing the tool can tell the operator at
    that moment -- and offer to re-prompt via -Force rather than making them
    restart the console.

--------------------------------------------------------------------------------
SCOPE -- THIS IS THE PART THAT WILL BITE YOU
--------------------------------------------------------------------------------

THE CACHE MUST LIVE IN $global:, NOT $script:.

The console launches tools with the call operator, and in that arrangement
Common.ps1's script scope IS NOT the calling tool's script scope. A $script:
read from a launched tool resolves to $null and the operator is prompted on
every single call.

This is not a new discovery. Add-ReportFileControls in Common.ps1 already
carries a comment recording the same trap, and it is the reason that function
returns state on an object instead of stashing it. Read that comment.

    $global:ToolkitApiSecrets   hashtable, service name -> entry

Initialise defensively -- if it does not exist, create it -- because any tool
may be the first caller in a session.

TOOLS THAT RUN IN THEIR OWN PROCESS CANNOT SHARE THIS. Anything carrying
"# TOOLKIT-REQUIRES: OwnProcess" gets a separate PowerShell process with a
separate global scope and will prompt every time. That is correct behaviour,
not a bug -- but it means NO TOOL THAT CONSUMES AN API CREDENTIAL MAY CARRY
THAT MARKER. None of these tools has any reason to need its own process. Put a
comment saying so at the top of each when they are built, so nobody adds the
marker later without understanding what it costs.

--------------------------------------------------------------------------------
BEHAVIOUR
--------------------------------------------------------------------------------

  LAZY. Nothing happens at console startup. The prompt fires on the first call
  to Get-ApiSecret for that service in that session, and only for that service.
  An operator who only releases a quarantined message is never asked for the
  SendGrid or SER credentials.

  CACHED FOR THE SESSION. Subsequent calls return the cached entry without a
  dialog. -Force bypasses the cache and re-prompts, for a key rotated
  mid-session or mistyped.

  CANCEL IS A FIRST-CLASS ANSWER. Cancelling returns Ok = false with a Reason
  and caches nothing. The calling tool shows a normal cancelled state -- not an
  error dialog, not a stack trace, and never by proceeding with an empty
  credential and letting the API return 401.

  NO DISK. Get-ApiSecret must not read or write any file. Not a cache file, not
  a temp file, not a "remember me" option. There is deliberately no persistence
  parameter, because a parameter that exists will eventually be used.

--------------------------------------------------------------------------------
THE DIALOG
--------------------------------------------------------------------------------

Model it on Show-TargetPromptDialog in Common.ps1 -- same construction, sizing,
OK/Cancel arrangement and red error label. Do not invent a new dialog style.

Differences:

  * Secret fields set UseSystemPasswordChar = $true.
  * The title names the service, using Label from the table.
  * A grey hint line carries Help from the table, so the operator knows where
    in the vendor console to get the value.
  * A second grey line reads, verbatim:

        Held in memory for this session only. Never written to disk.

    Put it on the dialog, not only in the help. The person typing a credential
    into a window is entitled to know what happens to it, and that is the
    moment they are thinking about it.

  * OK is disabled while any required field is empty. An empty credential
    submitted by accident produces a 401 several seconds later in a completely
    different part of the tool, and that is a miserable thing to diagnose.

Clear the plaintext TextBox.Text immediately after building the SecureString.

BE HONEST IN THE CODE COMMENT ABOUT WHAT THAT DOES AND DOES NOT ACHIEVE. A
WinForms TextBox.Text is a managed .NET string: immutable, and it stays in
memory until the garbage collector gets to it. Clearing the control does not
scrub it. We do it anyway because it removes the value from the visible control
and from anything that later reads the form, and because the alternative is
leaving it there indefinitely. Write that reasoning down. DO NOT write a comment
claiming the plaintext has been securely erased, because it has not, and a
comment that overstates a control is worse than no comment -- somebody will rely
on it.

--------------------------------------------------------------------------------
USING A SECRET AT THE CALL SITE
--------------------------------------------------------------------------------

Provide ONE helper and require every caller to use it:

    Invoke-WithApiSecret -Secret <SecureString> -ScriptBlock { param($plain) ... }

It converts to plaintext, invokes the block, and clears the unmanaged buffer in
a finally, whether the block threw or not:

    $bstr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($Secret)
    try {
        $plain = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($bstr)
        & $ScriptBlock $plain
    } finally {
        [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($bstr)
    }

The plaintext exists for the shortest possible window and the unmanaged buffer
is always freed. WITHOUT THE finally, A FAILED API CALL LEAKS THE BUFFER --
which is exactly the path most exercised while a new integration is being
debugged.

Callers must never convert a SecureString themselves. If Test-Toolkit finds
SecureStringToBSTR anywhere outside this helper, that is a failure.

--------------------------------------------------------------------------------
THE THREE THINGS THAT MUST NEVER HAPPEN
--------------------------------------------------------------------------------

  1. NO SECRET IS EVER WRITTEN TO DISK. No file, ever, by any path. This
     includes the SER bearer token.

  2. NO SECRET IS EVER DISPLAYED. Not in output, not in an error, not in a
     progress line, not in a debug trace.

     THE SPECIFIC HAZARD IS ERROR HANDLING. Invoke-RestMethod failures can
     surface request detail, and a handler that dumps the exception verbatim
     can print an Authorization header. Write Get-SafeApiError, which takes an
     exception and returns display text with any Bearer token, any Basic
     credential, and any 32-or-more-character token-shaped run replaced by
     [redacted]. Route EVERY API catch block through it. No exceptions --
     including the ones you are certain are harmless, because those are the
     ones that get copied into new code.

  3. NO SECRET IS EVER AUDITED. The audit row records the tool, the operator,
     the target and the result, exactly as every other tool does, via
     Get-LogTarget. What authenticated the call is not part of any question the
     audit log exists to answer.

--------------------------------------------------------------------------------
WRITE-PATH RULES -- SPECIFY THESE NOW, ENFORCE THEM WHEN THE TOOLS ARE BUILT
--------------------------------------------------------------------------------

Two write operations will exist across these platforms. Neither is built in this
task. Both are written into the self-test NOW so that no future tool can
introduce them incorrectly.

  QUARANTINE RELEASE (Proofpoint POD)

    * ONE MESSAGE PER ACTION. No bulk release, no release-all, no release by
      result set. If ten messages need releasing that is ten confirmed actions.
    * The confirmation shows classification, sender, subject and recipient
      BEFORE the operator confirms. This is a security control being overridden
      and the decision must be informed.
    * Write-CompletedLog on success and Write-FailedLog on failure, with the
      message identifier and recipient as target via Get-LogTarget.

  SUPPRESSION REMOVAL (SendGrid)

    * ONE NAMED ADDRESS PER ACTION.
    * THE BULK ENDPOINTS ARE FORBIDDEN. SendGrid exposes calls that delete an
      entire suppression list in one request. No tool in this toolkit calls
      them, ever. There is no undo.
    * The tool shows WHICH LIST the address is on before removal -- a hard
      bounce and a spam complaint are different decisions.
    * Write-CompletedLog / Write-FailedLog with the address as target.

    if     (cached and -not $Force)  { return cached }
    elseif ($script:UseCcp)          { return Get-ApiSecretFromCcp ... }

I do not know our CCP endpoint or its parameter surface, and I am not willing to

Record all five unknowns in UNVERIFIED.md, alongside the Proofpoint POD

CONSOLE INTEGRATION
--------------------------------------------------------------------------------

Add a "Forget API credentials" item calling Clear-ApiSecret with no arguments,

Settings-adjacent, not a toolbar button.

It exists for the case where someone else needs the workstation, or a credential

something the operator can act on rather than just be told.

--------------------------------------------------------------------------------
SELF-TEST RULE
--------------------------------------------------------------------------------

Add SEC001 to Test-Toolkit -- a new prefix. Existing prefixes are WF, CMD, ENC
and LOG, and this belongs under none of them.

SEC001 fails when any .ps1 in the toolkit:

  a) writes a value obtained from Get-ApiSecret or Get-SerAccessToken to any
     file;
  b) calls SecureStringToBSTR outside Invoke-WithApiSecret;
  c) passes a credential result into Write-CompletedLog, Write-FailedLog, or
     any Out-File / Set-Content / Add-Content / Export-Csv / Export-Clixml;
  d) contains a literal that looks like a credential. A SendGrid key begins
     'SG.' -- a specific, checkable string, and exactly what a hurried paste
     into a script would leave behind. Worth a regex on its own;
  e) calls a SendGrid bulk suppression-deletion endpoint, or a Proofpoint bulk
     or release-all quarantine endpoint, in any form.

(d) and (e) are the two that will actually catch something one day. Static
analysis of data flow in PowerShell is imperfect and this rule will not catch
every path -- SAY SO IN ITS DESCRIPTION rather than implying it is exhaustive.
